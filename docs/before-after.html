Blazor + LaunchDarkly: before and after

"Before" is a standard Blazor app with no flag service. "After" is this PoC. Client side and server side are covered separately.

What this demo does

One Blazor WebAssembly page (Pages/Home.razor) that reads LaunchDarkly flags from C# and reacts to them live.

Part A · Client side (Blazor WebAssembly in the browser)

A0. How a basic Blazor WebAssembly app works

The whole app, including the .NET runtime, is downloaded and runs inside the browser. The server only serves static files.

  • Everything is public. Config and DLLs are downloaded to the browser, so only a client-side ID can live there, never an SDK key.
  • One thread. Code that blocks waiting on the network freezes the app.
  • Browser networking only. All HTTP goes through the browser's fetch; no raw sockets or file storage. This is why the .NET client SDK breaks (see A4).

A1. Client config

Before

Program.cs, default host. No flag settings.

var builder = WebAssemblyHostBuilder.CreateDefault(args);
builder.RootComponents.Add<App>("#app");
builder.RootComponents.Add<HeadOutlet>("head::after");
builder.Services.AddScoped(sp => new HttpClient {
    BaseAddress = new Uri(builder.HostEnvironment.BaseAddress) });

await builder.Build().RunAsync();
After

wwwroot/appsettings.json, client-side ID (public by design):

{
  "LaunchDarkly": {
    "ClientSideId": "YOUR_CLIENT_SIDE_ID",
    "InitTimeoutSeconds": 5,
    "LogLevel": "info"
  }
}

Program.cs registers the facade and initializes it before the first render:

builder.Services.Configure<LaunchDarklyOptions>(
    builder.Configuration.GetSection("LaunchDarkly"));
builder.Services.AddSingleton<LaunchDarklyClient>();
builder.Services.AddSingleton<ILaunchDarklyClient>(
    sp => sp.GetRequiredService<LaunchDarklyClient>());

var host = builder.Build();
// loading gate: no flicker on first paint
await host.Services.GetRequiredService<ILaunchDarklyClient>()
    .InitializeAsync();
await host.RunAsync();

What each added file does

Listed in the order a flag value travels: settings, then the C# side, then JS, then the SDK, then the UI.

FileWhat it does
wwwroot/appsettings.json
settings		 Holds the LaunchDarkly section: client-side ID, init timeout (5 seconds), log level. Downloaded by the browser, so it only ever contains the public client-side ID. Variants for local testing: appsettings.Stub.json points the SDK at the local stub; appsettings.StubBootstrap.json also turns on server bootstrap.
LaunchDarkly/LaunchDarklyOptions.cs
typed settings		 C# class the LaunchDarkly section binds to. Optional settings include BootstrapUrl, SdkModuleUrl (use a CDN), custom endpoints and event settings. ToJsOptions() converts them into the JS SDK's options object and leaves out anything not set, so the SDK's defaults apply.
LaunchDarkly/ILaunchDarklyClient.cs
contract		 The only thing pages and components depend on. Defines:
  • Typed reads: BoolVariation, StringVariation, IntVariation, DoubleVariation, JsonVariation<T>, VariationDetail, AllFlags
  • Change notifications: FlagChanged event, OnFlagChange(key, callback) for one flag
  • Actions: IdentifyAsync (switch user), TrackAsync (events), FlushAsync
Because components only see this interface, it can be mocked in tests or swapped for a native .NET SDK if issue #58 is ever fixed.
LaunchDarkly/LaunchDarklyClient.cs
C# facade		 Implements the interface.
  • Startup (InitializeAsync): loads the JS bridge. If BootstrapUrl is set, fetches context, hash and starting flags from the server first, falling back to an anonymous user if that fails. Then starts the JS SDK.
  • Reading flags: each variation call goes straight to JS synchronously (WASM supports in-process interop). Returns the default if the module isn't loaded. JSON flags are converted to your C# type; a wrong shape falls back to the default instead of crashing.
  • Callbacks from JS: [JSInvokable] methods OnFlagsChanged, OnFlagChanged, OnError raise the FlagChanged event that makes components re-render.
  • Cleanup: DisposeAsync flushes events and closes the SDK.
LaunchDarkly/LdModels.cs
data shapes		 What passes between C# and JS:
  • LdContexts: helpers to build a user or anonymous context
  • Result records: LdInitResult, LdIdentifyResult, LdFlushResult, FlagsChangedEventArgs
  • LdEvaluationDetail / LdEvaluationReason: why a flag returned its value
  • LdBootstrapPayload: the server's { context, hash, flags } response
wwwroot/js/launchdarkly-interop.js
JS bridge		 The only code that talks to the LaunchDarkly SDK directly.
  • initialize(): imports the vendored SDK, creates the client, subscribes to change and error before starting (so no update is missed), starts with bootstrap data and hash if any, then waits for initialization.
  • Exports one function per SDK call (boolVariation, identify, track, flush, ...) for C# to call.
  • Calls back into C# (OnFlagsChanged) when the SDK reports changes.
  • Flushes events when the tab is hidden or closed, so events aren't lost.
wwwroot/lib/launchdarkly/js-client-sdk-4.13.0.js
+ LICENSE.txt
LaunchDarkly JS SDK		 The official SDK, copied into the app instead of loaded from a CDN: no third-party runtime dependency, Content Security Policy friendly, deliberate upgrades. package.json pins the version and has a vendor-ld-sdk script to refresh the copy.
Components/FeatureFlag.razor
on/off component		 <FeatureFlag Key="new-checkout">…<Off>…</Off></FeatureFlag>. Reads the boolean flag and renders the main content or the Off content. Listens for FlagChanged and re-renders when its own flag changes.
Program.cs
changed		 Binds LaunchDarklyOptions, registers LaunchDarklyClient as a singleton behind ILaunchDarklyClient, and calls InitializeAsync() before the app renders. This loading gate stops flags flickering from defaults to real values.
_Imports.razor
changed		 Adds @using BlazorLdPoc.Client.LaunchDarkly and @using BlazorLdPoc.Client.Components, so every page can use ILaunchDarklyClient and <FeatureFlag>.
Pages/Home.razor
demo page		 Not part of the integration. Reads the four flags, counts change events, and has the Identify and Track buttons.

A4. Why the JS SDK and not the .NET client SDK?

The LaunchDarkly .NET client-side SDK is not supported in Blazor WebAssembly (launchdarkly/dotnet-core#58, open). The JS SDK sits behind ILaunchDarklyClient, so it can be swapped for a native .NET SDK later without changing components.

Part B · Server side (ASP.NET Core)

B1. Server config

Before

No flag settings.

After

The SDK key is a secret. Keep it out of source and out of wwwroot; use user-secrets locally and environment variables or a vault in deployed environments:

dotnet user-secrets set "LaunchDarkly:SdkKey" "sdk-xxxxxxxx"
# or
export LaunchDarkly__SdkKey="sdk-xxxxxxxx"

Program.cs registers one shared server SDK client:

var sdkKey = builder.Configuration["LaunchDarkly:SdkKey"];
builder.Services.AddSingleton<ILdClient>(_ =>
    new LdClient(Configuration.Builder(sdkKey)
        .StartWaitTime(TimeSpan.FromSeconds(5)).Build()));
